# 2026-11-08 决赛串口失分复盘

## 一句话结论

模块能收能发、波特率也对，但发的是我们自己设计的 `$VD` ASCII 帧，
平台要的是 `0x55` 开头的二进制帧——协议口径没对上，所以平台判为“没有通信”。

## 现场证据

- 抓包文件：`测试\V6C\serial_log_20261108_115354_522_COM3_9600_001.txt`
- 同一时刻的原始字节：`测试\V6C\serial_rx_20261108_115347.bin`（374744 字节）
- 统计结果：约 6.5 分钟收到 **10706 帧 `$VD,...`**，整段数据里 **0x55 出现 0 次**
- 帧例：`$VD,0912,00000,00051,1,0,000,9,1C\r\n`

说明链路本身是通的：9600 波特率正确、TX 有输出、数据完整可解析，
失分点只在“帧格式”。

## 时间线

| 时间 | 动作 | 结果 |
|---|---|---|
| 11:45 | `config.h` 把 `COMP_BAUD` 改为 9600 | 波特率正确 |
| 11:51~11:53 | 用 COM3 @9600 抓比赛口 | 连续收到 `$VD` 帧 |
| 12:00 | 才修改 `output.cpp`，尝试改成 0x55 帧 | 为时已晚，且该版有语法错误、编译不过 |

那版错误代码：

```c
snprintf(body, sizeof(body), "%d,%03u,%03u,%u", 0x55,
         (int)(fq*0., fq-(int(fq)) ss, ct?0x01:0x00);
```

括号与逗号都不成立，说明当时是在高度紧张下直接改格式串，没有经过编译验证。

## 根因

1. 赛前协议一直停留在“草案 / 待与组委会核对”，`$VD` 是我们的自定格式，
   35 字节、ASCII、XOR 校验——设计得很完整，但平台不认。
2. 现场才发现平台口径是 `0x55` 二进制帧，改动发生在比赛结束之后。
3. 没有“平台实机抓 hex 对照”这一步，自测只证明了自己发得对，
   没有证明对方收得懂。

## 现场要求的帧

9600 8N1：

```
0x55 | 振动整数 | 振动小数 | 启停 | 接触 | 停止位
```

- 振动频率按 0.1Hz 拆分，例如 165.2Hz → `165, 2`
- 启停：`1` = 振动中，`0` = 停
- 接触：`1` = 接触，`0` = 未接触
- 停止位：代码按帧尾字节 `0x0D` 实现；若平台指的是 UART 的 1 位停止位
  （帧只有前 5 字节），把 `COMP_FRAME_TRAILER_EN` 改为 `0` 重新编译

## 赛后修复

- `config.h`：新增 `COMP_FRAME_HEADER`（0x55）、`COMP_FRAME_TRAILER_EN`、`COMP_FRAME_TRAILER`（0x0D）
- `output.cpp`：`compBuildFrame()` 改为输出上述二进制帧，频率按 0.1Hz 四舍五入，
  无效频率发 `0,0`
- `test\comp_frame_test.cpp`：按新帧重写断言
- 宿主测试：6 字节版 `24 pass / 0 fail`；`-DCOMP_FRAME_TRAILER_EN=0` 的 5 字节版 `22 pass / 0 fail`
- `test\run_all.ps1`：五项全 OK、0 warning

## 教训（下次直接照做）

1. **接口协议必须在赛前拿到最终版**，不能带着“草案”上场。
2. **对接验证要抓 hex**：不是看串口助手能不能显示，而是逐字节比对平台收到的数据。
3. **改协议后先编译再烧录**，现场改完必须留一次 `compile` 通过的记录。
4. **留一发“兜底固件”**：二进制帧和文本帧各准备一版，现场按平台口径切换。
5. 赛前检查表加一条：*用平台的接收端（或复刻解析脚本）跑通一帧，再开始比赛*。
